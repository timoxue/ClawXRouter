# EdgeClaw Router — 互联协同典型应用

我们以 EdgeClaw Router 插件作为端云互联协同的一个典型应用场景。

我们将 EdgeClaw Router 插件拆分为四层：


| 层         | 职责                        |
| --------- | ------------------------- |
| **检测层**   | 判断消息等级——安全等级或任务复杂度        |
| **路由层**   | 根据检测结果做出路由决策——用哪个模型、走哪条路径 |
| **执行层**   | 执行路由决策——转发云端、脱敏代理、本地隔离处理  |
| **状态管理层** | 维护会话、记忆、配置等运行时状态          |


每一层可独立测试、独立替换，确保用户可以充分自定义，降低开发门槛。

作为预设，我们设计了两个内置路由器：**隐私安全路由**与**性价比路由**，分别旨在解决用户隐私安全问题与成本问题。下面按照四层结构分别讲解。

---

## 一、检测层

检测层的职责是对每条消息进行分析，产出一个结构化的检测结果。隐私安全路由和性价比路由各自有独立的检测逻辑，关注不同的维度。

### 1.1 隐私安全路由的检测

隐私安全路由需要判断一条消息是否涉及敏感信息，并将其分为三个等级：


| 等级          | 语义                | 示例                         |
| ----------- | ----------------- | -------------------------- |
| **S1** — 安全 | 不含任何敏感信息          | "HTTP 403 和 401 有什么区别？"    |
| **S2** — 敏感 | 含可脱敏的 PII（个人身份信息） | 含内网 IP 的 SOC 告警、含手机号的联系人信息 |
| **S3** — 私密 | 含不可脱敏的机密信息        | SSH 私钥、硬编码密码、工资单、病历        |


> **为什么是三级？** 三级对应三条完全不同的物理执行路径（云端 / 脱敏代理 / 本地隔离），每个等级的行为清晰可预测。若只有两级（安全/不安全），会把可脱敏的 S2 数据也强制在本地处理，浪费了云侧的推理能力；若用连续评分（0.0~1.0），用户无法直觉理解不同分数对应什么行为。

我们采用**双检测引擎**：基于规则的检测与基于端侧大语言模型的检测。

```
输入消息 ──→ 规则检测器 (关键词 + 正则) ──→ S1/S2/S3
         └─→ LLM 检测器 (端侧小模型)    ──→ S1/S2/S3
                                                │
                                                ▼
                                          max(两者) = 最终等级
```

#### 1.1.1 规则检测器

规则检测基于**关键词与正则表达式**，便于用户根据使用场景自定义。其核心特征是：零成本、零延迟、确定性高。

规则检测器覆盖四个维度：


| 维度           | 检测对象            | 示例规则                                      |
| ------------ | --------------- | ----------------------------------------- |
| **关键词匹配**    | 消息文本中的敏感词       | `password`→S2, `ssh`→S3, `private_key`→S3 |
| **正则匹配**     | 消息文本中的结构化模式     | 内网 IP `10.x.x.x`→S2, AWS Key `AKIA...`→S3 |
| **工具名匹配**    | Agent 发起的工具调用名称 | `execute_command`→S3                      |
| **工具参数路径匹配** | 工具参数中的文件路径      | `~/.ssh/`→S3, `/etc/passwd`→S3, `.pem`→S3 |


前两个维度检测"消息说了什么"（内容安全），后两个维度检测"消息要做什么"（行为安全）。例如一条看似无害的消息，其触发的工具调用可能包含 `rm -rf /`——仅检测消息内容无法发现这类风险。

```
function ruleDetect(message, toolName, toolParams, config):
    results = []

    // 维度一：关键词匹配
    for keyword in config.s3Keywords:
        if message.toLowerCase().includes(keyword):
            results.push(S3, "hit S3 keyword: " + keyword)
    for keyword in config.s2Keywords:
        if message.toLowerCase().includes(keyword):
            results.push(S2, "hit S2 keyword: " + keyword)

    // 维度二：正则匹配
    for pattern in config.s3Patterns:
        if regex(pattern).test(message):
            results.push(S3, "hit S3 pattern: " + pattern)
    for pattern in config.s2Patterns:
        if regex(pattern).test(message):
            results.push(S2, "hit S2 pattern: " + pattern)

    // 维度三：工具名匹配
    if toolName:
        if toolName in config.s3DangerousTools:
            results.push(S3, "S3 dangerous tool: " + toolName)
        else if toolName in config.s2SensitiveTools:
            results.push(S2, "S2 sensitive tool: " + toolName)

    // 维度四：工具参数中的文件路径匹配
    paths = extractPaths(toolParams)
    for path in paths:
        if matchesAny(path, config.s3Paths):
            results.push(S3, "S3 sensitive path: " + path)
        if path.endsWith(".pem", ".key", "id_rsa"):
            results.push(S3, "sensitive file type: " + path)

    // 取所有命中的最高等级
    if results is empty:
        return { level: S1, confidence: 1.0 }
    return { level: max(results.allLevels), reason: join(results.allReasons), confidence: 1.0 }
```

用户可通过配置文件自定义规则，例如限制某些目录不允许云侧模型访问：

```json
{
  "rules": {
    "keywords": { "S2": ["客户编号"], "S3": ["社保号", "银行卡"] },
    "patterns": { "S3": ["AKIA[0-9A-Z]{16}"] },
    "tools": { "S3": { "tools": ["execute_command"], "paths": ["/etc/shadow", "~/.ssh/"] } }
  }
}
```

#### 1.1.2 LLM 检测器

基于端侧大语言模型的检测使用用户自定义的检测 prompt，泛化性更强。对于规则无法覆盖的长尾场景——例如"帮我分析这份工资单"中没有任何关键词或模式匹配，但语义上是高度私密的——LLM 检测器有更高的召回率。

LLM 检测器的工作方式：

1. 将用户消息与检测 system prompt 组合发送给端侧小模型（如 Qwen 7B、MiniCPM 4.1）
2. 模型返回结构化 JSON 响应：`{"level":"S1|S2|S3","reason":"简述理由"}`
3. 若判定为 S2，检测器同时返回脱敏后的版本（在同一次调用中完成检测和脱敏，减少调用次数）

检测 prompt 可通过 `prompts/detection-system.md` 自定义，其核心规则包括：

- 密码/凭证 → 始终 S3（不可降级为 S2）
- 医疗数据 → 始终 S3
- 地址、手机号、邮箱 → S2（可脱敏）
- 仅仅是文件操作（读写普通 .txt/.md）且消息中没有 PII → S1
- 不对未知文件内容做推测——仅根据消息中实际出现的数据判定

```
function llmDetect(message, config):
    // 构建检测 prompt
    systemPrompt = loadPrompt("detection-system.md", DEFAULT_DETECTION_PROMPT)

    // 调用端侧小模型
    response = callLocalModel(
        endpoint: config.localModel.endpoint,    // e.g. http://localhost:11434
        model:    config.localModel.model,        // e.g. qwen2.5:7b
        messages: [
            { role: "system", content: systemPrompt },
            { role: "user",   content: message }
        ],
        temperature: 0,
        providerType: config.localModel.type      // openai-compatible / ollama-native / custom
    )

    // 解析 JSON 响应
    parsed = JSON.parse(response)                 // {"level":"S2","reason":"含手机号"}

    // 如果 S2，同一次调用中已返回脱敏版本
    if parsed.level == S2:
        return { level: S2, reason: parsed.reason, desensitized: parsed.desensitized }

    return { level: parsed.level, reason: parsed.reason }
```

LLM 检测器支持多种 API 协议接入（`openai-compatible`/`ollama-native`/`custom`），适配 Ollama、vLLM、LMStudio 等主流端侧推理后端。

#### 1.1.3 双引擎协作

对于双引擎不同的判别结果，我们**优先取严格的结果**（即取 max）。这个设计背后的考量是：

- **规则引擎是下限保障**：对已知模式（IP、API Key、SSH 密钥格式），规则检测器准确率 > 99%，且零延迟零成本。这些"硬模式"不需要 LLM 参与。
- **LLM 引擎是上限提升**：对规则无法覆盖的语义场景（"分析这份体检报告"、"帮我看看工资条"），LLM 能通过上下文理解识别敏感意图。
- **取 max 保证不遗漏**：宁可误判为高等级（多一次本地处理），也不漏判为低等级（敏感数据意外上云）。

此外，如果规则引擎已经判定 S3（例如匹配到 AWS Key），协调器可以跳过 LLM 调用——因为结果不可能比 S3 更高，节省端侧计算资源。

```
function privacyDetector(context, config):
    // 获取当前 checkpoint 应启用的检测器列表
    detectors = config.checkpoints[context.checkpoint]
    // 默认: ["ruleDetector", "localModelDetector"]

    results = []

    for detector in detectors:
        try:
            if detector == "ruleDetector":
                result = ruleDetect(context.message, context.toolName, context.toolParams, config)
            else if detector == "localModelDetector":
                result = llmDetect(context.message, config)
            results.push(result)
        catch error:
            log.warn("detector " + detector + " failed, skip")
            continue

    // 合并：取最高安全等级
    if results is empty:
        return { level: S1, reason: "no detection results" }

    finalLevel = max(r.level for r in results)
    primary = results.find(r => r.level == finalLevel)
    return { level: finalLevel, reason: join(all reasons), detector: primary.detector }
```

### 1.2 性价比路由的检测

性价比路由关注的不是安全等级，而是**任务复杂度**——用户这条消息需要多强的推理能力？

我们采用 **LLM-as-Judge**（小模型裁判）方案，将任务分为四个复杂度等级：


| Tier          | 能力需求            | 典型示例                     |
| ------------- | --------------- | ------------------------ |
| **SIMPLE**    | 查找、翻译、格式化、是/否判断 | "什么是 YAML？"、"把这段翻译成英文"   |
| **MEDIUM**    | 代码生成、单文件分析、摘要   | "找出这个函数的 bug"、"总结这篇文档"   |
| **COMPLEX**   | 系统设计、多文件重构、架构决策 | "设计百万 QPS 推送系统"、"重构数据库层" |
| **REASONING** | 数学证明、形式推理、深度分析  | "证明梅森素数指数必须是素数"、"识别研究空白" |


> **为什么用 LLM-as-Judge 而不是关键词规则？** 任务复杂度是语义维度的判断——"包含代码"不等于"复杂"（一个 10 行 bug fix 是 MEDIUM，50 个文件的重构是 COMPLEX）。关键词规则无法区分。而用被路由的大模型自己判断则会导致成本翻倍，违背了性价比路由的初衷。用小模型做 Judge，成本约为大模型的 1/20，只要能将 50%+ 的消息下调到 SIMPLE tier，净节省就很显著。

> **为什么是四级？** 四级对应四种显著不同的能力需求和成本量级（SIMPLE 的费用约为 REASONING 的 1/20）。更少会导致细粒度不足，更多会增加 Judge 的判断错误率。四级是分级收益与判断准确率的平衡点。

Judge 模型使用可自定义的 system prompt（`prompts/token-saver-judge.md`），其核心分类规则包括：

- 不确定时选较低等级（节省 token）
- 短 prompt（< 20 词）且无技术深度 → SIMPLE
- 仅包含代码片段不意味着 COMPLEX——短代码 review 是 MEDIUM
- 涉及多源交叉引用或设计新方案 → COMPLEX 或 REASONING
- 明确要求"识别空白"、"设计实验"、"证明" → REASONING

```
function tokenSaverDetect(context, config):
    // subagent 会话直接跳过，不做分级
    if context.sessionKey.includes(":subagent:"):
        return { level: S1, action: passthrough, reason: "subagent session, skip" }

    message = context.message
    if message is empty:
        return { level: S1, action: passthrough }

    // 查缓存：相同消息不重复调 Judge
    cacheKey = SHA256(message).slice(0, 16)
    if cache[cacheKey] exists and not expired(TTL=5min):
        return buildDecision(cache[cacheKey].tier)

    // 调用 LLM Judge
    try:
        judgePrompt = loadPrompt("token-saver-judge.md", DEFAULT_JUDGE_PROMPT)
        response = callLocalModel(
            endpoint: config.judgeEndpoint,
            model:    config.judgeModel,        // e.g. gemini-2.5-flash
            messages: [
                { role: "system", content: judgePrompt },
                { role: "user",   content: message }
            ],
            temperature: 0
        )
        tier = parseTier(response)              // 从 {"tier":"SIMPLE"} 中提取
        cache[cacheKey] = { tier, timestamp: now() }

        target = config.tierMapping[tier]       // e.g. SIMPLE → gemini-2.5-flash
        return { level: S1, action: redirect, target: target, reason: "tier=" + tier }
    catch error:
        log.error("Judge call failed, passthrough to default model")
        return { level: S1, action: passthrough, reason: "judge call failed" }

function parseTier(responseText):
    // 移除模型可能输出的 <think> 思考标签
    cleaned = removeThinkTags(responseText)
    // 正则提取 tier 字段
    match = regex('{"tier":"([A-Z]+)"}').exec(cleaned)
    if match and match[1] in {SIMPLE, MEDIUM, COMPLEX, REASONING}:
        return match[1]
    // 解析失败时降级到 MEDIUM（不是最贵也不是最便宜）
    return MEDIUM
```

检测层还包含两个优化机制：

1. **Prompt Hash 缓存**：对消息内容计算 SHA-256 哈希作为 cache key（TTL 5 分钟），相同或相似消息不重复调用 Judge，避免重试场景下的浪费。
2. **Subagent 豁免**：子代理会话自动跳过分级——一次主任务可能拆分出 10-50 条子消息，逐条调 Judge 开销巨大且无意义。

## 二、路由层

路由层的职责是将检测层的结果映射为具体的路由决策（用哪个模型、走哪条路径），并在多个路由器产出不同意见时进行合并裁决。

### 2.1 路由管线：可组合的多路由器架构

路由层的核心是一个**可组合路由管线**（Router Pipeline）。管线内部可注册多个路由器，每个路由器独立运行、独立产出决策，最后由管线统一合并。

```typescript
interface GuardClawRouter {
  id: string;
  detect(context: DetectionContext, config: Record<string, unknown>): Promise<RouterDecision>;
}
```

每个路由器返回一个 `RouterDecision`，包含：

- `level`：安全等级（S1/S2/S3）
- `action`：建议行为（passthrough / redirect / transform / block）
- `target`：目标模型（provider + model）
- `reason`：决策理由

> **为什么是管线模式而不是单一路由器？** 安全检测和成本优化是两个完全不同的关注点——安全检测需要高优先级和短路行为，成本优化需要 LLM 判断（较慢）且只在安全通过后才有意义。如果把所有逻辑写在一个路由器里，添加新能力（如内容过滤、合规检查）就必须修改核心代码。管线模式让每个路由器只关注自己的判断维度，可独立测试、独立替换。

### 2.2 隐私安全路由的路由决策

隐私安全路由（Privacy Router）接收检测层的三级结果（S1/S2/S3），映射为具体的路由行为：


| 检测结果             | 路由决策                          | 目标                           |
| ---------------- | ----------------------------- | ---------------------------- |
| S1（安全）           | `passthrough` — 不干预，交给其他路由器决定 | 无（放行）                        |
| S2（敏感）+ proxy 策略 | `redirect` → 隐私代理             | `guardclaw-privacy` provider |
| S2（敏感）+ local 策略 | `redirect` → 本地模型             | 端侧推理后端（如 Ollama）             |
| S3（私密）           | `redirect` → Guard Agent      | 端侧推理后端（隔离的本地 Agent）          |


注意 S1 时返回的是 `passthrough`（"我没意见"），而非 `redirect`（"我建议用某个模型"）。这个语义区分是管线合并的关键——下文详述。

S2 提供了 `proxy` 和 `local` 两种策略可供用户选择，这是对不同风险偏好的尊重：

- **proxy 策略**：脱敏后通过本地代理转发给云端，适合需要云侧推理能力但消息含 PII 的场景
- **local 策略**：直接路由到端侧模型处理，适合风险厌恶型用户

> **为什么提供两种 S2 策略？** 因为"最优成本"是主观的。有的用户认为脱敏后可接受发送到云端（获得更好的推理质量），有的用户即使脱敏了也不想让数据离开本地。系统不替用户做风险决策，而是提供两条隔离程度不同的路径。

### 2.3 性价比路由的路由决策

性价比路由（Token-Saver Router）接收检测层的四级分类结果（SIMPLE/MEDIUM/COMPLEX/REASONING），映射为具体的模型选择：


| 检测结果      | 路由决策              | 默认目标模型            | 成本量级            |
| --------- | ----------------- | ----------------- | --------------- |
| SIMPLE    | `redirect` → 小模型  | gemini-2.5-flash  | ~$0.15/M tokens |
| MEDIUM    | `redirect` → 中等模型 | gemini-2.5-pro    | ~$1.25/M tokens |
| COMPLEX   | `redirect` → 大模型  | gemini-3.1-pro    | ~$2.50/M tokens |
| REASONING | `redirect` → 最强模型 | claude-sonnet-4.5 | ~$3.00/M tokens |


每个 tier 对应的模型由用户配置，这正是用户表达"性能-成本支点"偏好的方式：

```json
{
  "tiers": {
    "SIMPLE":    { "provider": "google", "model": "gemini-2.5-flash" },
    "MEDIUM":    { "provider": "google", "model": "gemini-2.5-pro" },
    "COMPLEX":   { "provider": "google", "model": "gemini-3.1-pro" },
    "REASONING": { "provider": "anthropic", "model": "claude-sonnet-4.5" }
  }
}
```

成本敏感型用户可以将 SIMPLE 和 MEDIUM 都映射到小模型；质量敏感型用户可以从 MEDIUM 就开始用大模型。

### 2.4 两阶段执行与短路优化

管线中的路由器不是同时运行的，而是分为两个阶段：

```
Phase 1: 快速路由器 (weight ≥ 50)
  ├─ 隐私安全路由 (weight=90)：规则检测 + LLM 检测，通常 < 500ms
  ├─ 若任一返回 S2/S3 → 短路，跳过 Phase 2
  └─ 若全部 S1 → 继续 Phase 2

Phase 2: 慢速路由器 (weight < 50)
  └─ 性价比路由 (weight=30)：调用 LLM Judge，约 1-2s
```

> **为什么不全部并行？** 当消息含隐私信息（S2/S3）时，性价比路由的分级结果毫无意义——无论任务是 SIMPLE 还是 REASONING，都必须走隐私路径。此时 LLM Judge 的调用纯属浪费。两阶段模型在架构上显式声明了：**安全是前提，成本优化是在安全通过后的第二级关注**。

```
function pipeline.run(checkpoint, context, pluginConfig):
    // 按 weight 分为快组和慢组
    fastGroup = []   // weight ≥ 50
    slowGroup = []   // weight < 50

    for routerId in getRoutersForCheckpoint(checkpoint):
        if not isEnabled(routerId): continue
        router = registeredRouters[routerId]
        weight = routerConfigs[routerId].weight    // privacy=90, token-saver=30
        if weight >= 50:
            fastGroup.push({ router, weight })
        else:
            slowGroup.push({ router, weight })

    // ── Phase 1: 并行运行快组 ──
    fastResults = await Promise.all(
        fastGroup.map(r => r.router.detect(context, pluginConfig))
    )

    // 检查是否有非 S1 的明确意见
    hasPrivacyConcern = fastResults.any(r => r.level != S1 and r.action != passthrough)

    if hasPrivacyConcern or slowGroup is empty:
        if hasPrivacyConcern and slowGroup is not empty:
            log.info("短路：跳过 " + slowGroup.map(r => r.id))
        return mergeDecisions(fastResults)

    // ── Phase 2: 快组全部 S1，继续运行慢组 ──
    slowResults = await Promise.all(
        slowGroup.map(r => r.router.detect(context, pluginConfig))
    )

    return mergeDecisions(fastResults + slowResults)
```

### 2.5 决策合并：当两个路由器意见不同时

管线按以下规则合并多个路由器的决策：

```
规则 1: 安全级别最高的胜出         S3 > S2 > S1
规则 2: 同级别下，权重高的胜出     privacy(90) > token-saver(30)
规则 3: 同权重下，行为严格的胜出   block > redirect > transform > passthrough
规则 4: passthrough 意味着"无意见"  主动让步给其他路由器的 redirect
```

```
function mergeDecisions(weightedDecisions):
    if list is empty:
        return { level: S1, action: passthrough, reason: "no decisions" }
    if list.length == 1:
        return list[0].decision

    // ── 规则1: 取最高安全等级 ──
    winningLevel = max(d.decision.level for d in list)    // S3 > S2 > S1

    // 筛选处于最高等级的决策
    atWinningLevel = list.filter(d => d.decision.level == winningLevel)

    // ── 规则2+3: 按 weight 降序，再按 action 严格度降序排序 ──
    atWinningLevel.sort(by: [weight DESC, actionPriority DESC])
    // actionPriority: block(4) > redirect(3) > transform(2) > passthrough(1)

    winner = atWinningLevel[0].decision

    // ── 规则4: passthrough 让步给 redirect ──
    // 当最高等级是 S1 且 winner 说 passthrough（无意见），
    // 但有其他路由器说 redirect（有明确目标），则让 redirect 生效
    if winningLevel == S1 and winner.action == passthrough:
        redirectCandidate = atWinningLevel.find(d => d.action == redirect and d.target != null)
        if redirectCandidate exists:
            winner = redirectCandidate.decision

    // 计算加权置信度
    weightedConfidence = Σ(d.confidence × d.weight) / Σ(d.weight)

    return {
        level:  winningLevel,
        action: winner.action,
        target: winner.target,
        reason: join(all non-S1 reasons),
        confidence: weightedConfidence
    }
```

规则 4 是关键。当隐私安全路由返回 S1/passthrough（"没有隐私问题，我没意见"），而性价比路由返回 S1/redirect（"请用 gemini-2.5-flash"）时，redirect 生效——尽管隐私路由的 weight 更高。

> **动机**：早期实现中曾出现一个 bug——隐私路由的 S1/passthrough 因 weight 更高覆盖了性价比路由的 redirect，导致性价比路由永远不生效。修复后明确了语义：`passthrough` = "我没意见，交给其他路由器"，`redirect` = "我建议用这个模型"。两者不是同一维度的竞争，而是"无意见"对"有主张"的让步关系。

这个合并策略产生了自然的协作行为：


| 场景          | 隐私路由              | 性价比路由              | 最终决策                            |
| ----------- | ----------------- | ------------------ | ------------------------------- |
| 简单问题，无隐私    | S1/passthrough    | S1/redirect→flash  | **性价比路由胜出** → gemini-2.5-flash  |
| 复杂推理，无隐私    | S1/passthrough    | S1/redirect→claude | **性价比路由胜出** → claude-sonnet-4.5 |
| 含内网 IP 的告警  | S2/redirect→proxy | （被短路跳过）            | **隐私路由胜出** → 脱敏代理               |
| 含 SSH 私钥    | S3/redirect→guard | （被短路跳过）            | **隐私路由胜出** → Guard Agent        |
| 含身份证 + 简单问题 | S2/redirect→proxy | SIMPLE（被短路跳过）      | **隐私路由胜出** → 脱敏代理               |

## 三、执行层

执行层负责将路由层的决策转化为实际的物理操作——将消息发送到正确的目标。

### 3.1 隐私安全路由的执行

隐私安全路由根据等级不同，有三条完全不同的执行路径：

#### 3.1.1 S1 — 直接通过

消息直接转发给云端模型，不做任何修改。此时性价比路由可能已在路由层指定了具体的云端模型（如 gemini-2.5-flash），执行层只需按指示转发。

#### 3.1.2 S2 — 隐私代理（proxy 策略）

执行层部署了一个本地 HTTP 反向代理（默认端口 8403），负责 S2 消息的脱敏转发：

```
Agent → guardclaw-privacy provider → localhost:8403 (本地代理)
  → stripPiiMarkers()  去除 <guardclaw-s2>...</guardclaw-s2> 标记
  → cleanToolSchemas()  修复不兼容的 JSON Schema
  → buildUpstreamUrl()  构建目标云端 API URL
  → resolveAuthHeaders() 添加认证头（OpenAI/Google/Anthropic 各不同）
  → fetch() 转发到云端
  → 流式/非流式响应透传返回
```

脱敏标记协议的工作方式：

```
原始消息：我的地址是北京市朝阳区建国路88号
        ↓ (端侧 LLM 脱敏 + 标记)
标记后：  我的地址是<guardclaw-s2>[某城市某区某路某号]</guardclaw-s2>
        ↓ (代理剥离标记)
云端收到：我的地址是[某城市某区某路某号]
```

> **为什么用本地代理而不是在构建请求时直接替换消息？** 两个原因：(1) 不同云端提供商的 API 格式不同（OpenAI 的 messages vs Google 的 contents vs Anthropic 的 x-api-key 认证），在请求构建层处理所有格式会导致代码膨胀；(2) 代理天然支持流式响应（SSE）的透传，而在 hook 中拦截和转发流式响应非常困难。代理模式将"消息清洗"和"API 适配"封装在一个独立的 HTTP 服务中，与路由逻辑解耦。

```
function privacyProxy.handleRequest(request):
    body = parseJSON(request.body)

    // 1. 剥离脱敏标记
    if body.messages:                                 // OpenAI 格式
        for msg in body.messages:
            if msg.role == "user":
                msg.content = stripPiiMarkers(msg.content)
                // "<guardclaw-s2>[某城市某区]</guardclaw-s2>" → "[某城市某区]"
    else if body.contents:                            // Google 格式
        for part in body.contents:
            part.text = stripPiiMarkers(part.text)

    // 2. 清理不兼容的 JSON Schema 字段（部分云端 API 不支持）
    cleanToolSchemas(body)

    // 3. 构建上游 URL
    target = consumeOriginalProvider(session) or defaultTarget
    upstreamUrl = buildUpstreamUrl(target)            // e.g. https://api.openai.com/v1/chat/completions

    // 4. 认证头
    headers = resolveAuthHeaders(target)
    // Anthropic → x-api-key, Others → Authorization: Bearer

    // 5. 转发
    response = fetch(upstreamUrl, { method: POST, headers, body })

    // 6. 透传响应（支持 SSE 流式）
    if response.headers["content-type"].includes("text/event-stream"):
        return pipeStream(response)
    else:
        return response.json()
```

代理支持三类上游提供商：

- **OpenAI 及兼容 API**：标准 messages + tools 格式
- **Google/Gemini**：contents + functionDeclarations 格式
- **Anthropic**：messages + x-api-key 认证方式

#### 3.1.3 S3 — Guard Agent（本地隔离执行）

S3 消息交由一个独立的 Guard Agent 处理。Guard Agent 是一个**物理隔离**的本地 Agent：


| 维度        | Guard Agent                    | 主 Agent                  |
| --------- | ------------------------------ | ------------------------ |
| Session   | `xxx:guard`（独立 session key）    | `xxx`                    |
| Workspace | `~/.openclaw/workspace-guard/` | `~/.openclaw/workspace/` |
| 模型        | 仅限本地（Ollama/vLLM/等）            | 可用云端                     |
| 历史记录      | 独立，不与主 Agent 共享                | 不包含 Guard Agent 的交互      |


Guard Agent 在创建时会校验目标 provider 是否在本地白名单中：

```
本地白名单: ollama, llama.cpp, localai, llamafile, lmstudio, vllm, mlx, sglang, tgi
```

只有白名单内的 provider 才被允许处理 S3 任务，防止配置错误导致敏感数据意外发送到云端。

```
function routeToGuardAgent(message, config):
    guardConfig = parseGuardAgentConfig(config)
    // e.g. "ollama/qwen2.5:7b" → { provider: "ollama", model: "qwen2.5:7b" }

    // 校验 provider 是否在本地白名单中
    LOCAL_PROVIDERS = {"ollama", "llama.cpp", "localai", "llamafile",
                       "lmstudio", "vllm", "mlx", "sglang", "tgi"}
    if guardConfig.provider not in LOCAL_PROVIDERS:
        log.error("Guard Agent provider not local: " + guardConfig.provider)
        return error("refusing to send S3 data to non-local provider")

    // 生成隔离的 session key
    guardSessionKey = currentSessionKey + ":guard"

    // 注入 Guard Agent 专用系统提示
    systemPrompt = loadPrompt("guard-agent-system.md", DEFAULT_GUARD_PROMPT)

    // 在隔离的 workspace 中执行
    return callModel(
        provider:  guardConfig.provider,
        model:     guardConfig.model,
        session:   guardSessionKey,
        workspace: "~/.openclaw/workspace-guard/",
        messages:  [{ role: "system", content: systemPrompt }, ...message]
    )
```

> **为什么不直接切换主 Agent 的模型到本地？** 如果只是切换模型，主 Agent 的上下文窗口仍然包含所有历史消息（含之前 S1 时发送给云端的内容）。当会话后续切回云端模型时，S3 内容可能因为上下文残留而泄露。Guard Agent 的物理隔离确保：S3 内容永远只存在于 Guard Agent 的上下文中，主 Agent 的 clean session 不包含任何 Guard Agent 的交互记录。

### 3.2 性价比路由的执行

性价比路由的执行相对简单——它不涉及消息内容的修改，只涉及**模型切换**。

路由层的 redirect 决策指定了 `{ provider, model }`，执行层通过 provider 镜像机制将请求转发到对应的模型。系统注册了一个 `guardclaw-privacy` 虚拟 provider，镜像其他 provider 的模型列表，使路由决策可以在不改变调用接口的情况下切换底层模型。

实际效果示例：


| 用户消息            | Judge 判定  | 执行层动作                   |
| --------------- | --------- | ----------------------- |
| "什么是 YAML？"     | SIMPLE    | 请求转发给 gemini-2.5-flash  |
| "找出这个函数的 bug"   | MEDIUM    | 请求转发给 gemini-2.5-pro    |
| "设计百万 QPS 推送系统" | COMPLEX   | 请求转发给 gemini-3.1-pro    |
| "证明梅森素数定理"      | REASONING | 请求转发给 claude-sonnet-4.5 |


### 3.3 两个路由器共享的集成机制：Hook 系统

执行层通过宿主 Agent 的 **Hook 系统**与消息生命周期对接。路由插件注册了 13 个 Hook 覆盖消息从接收到持久化的每个关键节点：


| 阶段         | 关键 Hook                | 隐私安全路由的行为                 | 性价比路由的行为              |
| ---------- | ---------------------- | ------------------------- | --------------------- |
| 模型选择前      | `before_model_resolve` | 执行路由管线，产出安全等级             | 执行 Judge 分级，产出 tier   |
| Prompt 构建前 | `before_prompt_build`  | 注入脱敏标记 / Guard Agent 系统提示 | 无特殊处理                 |
| 工具调用前      | `before_tool_call`     | 检测工具参数安全性，重定向记忆路径         | —                     |
| 工具调用后      | `after_tool_call`      | 检测工具返回内容，同步记忆             | —                     |
| 工具结果持久化    | `tool_result_persist`  | PII 脱敏，过滤记忆搜索结果           | —                     |
| 消息写入前      | `before_message_write` | 根据隐私状态清洗消息内容              | —                     |
| 会话结束       | `session_end`          | 同步所有记忆                    | 输出 token 统计           |
| LLM 输出     | `llm_output`           | —                         | 记录 token 统计（按 tier 分） |


```
// 核心 Hook：before_model_resolve
// 在 Agent 选择模型前触发，决定消息走哪个模型
hook before_model_resolve(context):
    decision = pipeline.run("onUserMessage", {
        checkpoint: "onUserMessage",
        message:    context.userMessage,
        sessionKey: context.sessionKey
    }, pluginConfig)

    if decision.action == redirect and decision.target:
        // 暂存检测结果，供后续 Hook 使用
        stashDetection(context.sessionKey, {
            level: decision.level,
            reason: decision.reason
        })
        // 记录原始 provider，代理需要知道转发目标
        if decision.level == S2:
            stashOriginalProvider(context.sessionKey, context.currentProvider)
        // 覆盖模型选择
        context.provider = decision.target.provider
        context.model    = decision.target.model
        markSessionAsPrivate(context.sessionKey, decision.level)

// 核心 Hook：before_prompt_build
// 在构建发送给模型的 prompt 前触发
hook before_prompt_build(context):
    detection = consumeDetection(context.sessionKey)
    if not detection: return

    if detection.level == S2:
        // 注入隐私提醒 + 脱敏标记
        context.systemPrompt += PRIVACY_S2_INSTRUCTION
        if detection.desensitized:
            context.userMessage = wrapWithMarkers(detection.desensitized)
    else if detection.level == S3:
        // 注入 Guard Agent 专用系统提示
        context.systemPrompt = loadGuardAgentSystemPrompt()
```

> **为什么用 Hook 而不是 Middleware 或 Wrapper？** Middleware 只能在请求流上插入逻辑，无法拦截工具调用返回值、记忆持久化等非请求流事件。Wrapper 侵入性强，与宿主 Agent 的具体实现耦合紧密。Hook 是宿主 Agent 提供的标准扩展点，覆盖消息生命周期的每个关键节点，且 Hook 之间通过 stash/consume 模式传递状态，避免全局状态污染。

## 四、状态管理层

状态管理层维护路由决策所需的运行时状态，以及由路由决策衍生的隔离状态。隐私安全路由和性价比路由各自需要不同的状态支撑。

### 4.1 隐私安全路由的状态管理

隐私安全路由需要管理三类状态：会话隐私状态、双轨记忆、双轨会话历史。

#### 4.1.1 会话隐私状态

每个会话维护一组隐私状态：


| 字段                 | 含义                  | 行为                                  |
| ------------------ | ------------------- | ----------------------------------- |
| `isPrivate`        | 该会话是否包含隐私内容         | S2 触发后不可自动降级；S3 不标记（Guard Agent 物理隔离） |
| `highestLevel`     | 会话中出现过的最高安全等级       | 只升不降（S1→S2→S3），用于统计和审计              |
| `detectionHistory` | 所有检测事件的时间线（最近 50 条） | 供审计和 Dashboard 展示                   |


**S2 与 S3 的不同处理**：

- **S2 → 永久标记 private**：S2 消息通过主 Agent 的会话处理（proxy 脱敏或本地路由），脱敏内容留在主 Agent 的上下文窗口中。如果后续切回云端模型，上下文中的 S2 痕迹会随之发送。因此一旦 S2 触发，会话永久保持 private 状态。

- **S3 → 不标记 private**：S3 消息被路由到 Guard Agent——一个物理隔离的本地 Agent（独立 session key、独立 workspace、独立历史记录）。S3 内容**永远不会进入主 Agent 的上下文窗口**。主 Agent 的 clean session 中不包含任何 Guard Agent 的交互记录。因此，后续 S1 消息可以安全地切回云端模型——云端模型看到的上下文是干净的。`highestLevel` 仍会记录 S3（用于统计和审计），但 `isPrivate` 不受影响。

> **所有 S3 场景均不标记 private**：S3 的设计原则是**始终交由 Guard Agent（子 agent）处理**，无论 S3 出现在哪个 checkpoint：
> - **用户消息级别**（`before_model_resolve`）：消息路由到 Guard Agent，主 Agent 上下文不含 S3 数据。
> - **工具调用级别**（`before_tool_call`）：工具被 block，S3 内容不会进入执行结果。
> - **工具结果级别**（`after_tool_call` / `tool_result_persist`）：S3 内容被 `before_message_write` 替换为占位符 `🔒 [Private content — processed locally]`，云端模型在后续上下文中只看到占位符。
>
> 因此，无论 S3 出现在哪里，主 Agent 的上下文窗口始终是干净的，`isPrivate` 不受影响。

```
function markSessionAsPrivate(sessionKey, level):
    state = sessionStates.get(sessionKey)
    shouldBePrivate = (level == S2 or level == S3)

    if state exists:
        state.isPrivate = state.isPrivate or shouldBePrivate
        state.highestLevel = max(state.highestLevel, level)
    else:
        sessionStates.set(sessionKey, {
            isPrivate: shouldBePrivate,
            highestLevel: level,
            detectionHistory: []
        })

// S3 路由到 Guard Agent 时，只更新 highestLevel，不标记 isPrivate
function trackSessionLevel(sessionKey, level):
    state = sessionStates.get(sessionKey)

    if state exists:
        state.highestLevel = max(state.highestLevel, level)
    else:
        sessionStates.set(sessionKey, {
            isPrivate: false,       // Guard Agent 物理隔离，主会话不受污染
            highestLevel: level,
            detectionHistory: []
        })
```

此外，状态管理层实现了 **Stash/Consume 机制**，用于在不同 Hook 之间传递检测结果：

```
// Hook A 产出检测结果 → 暂存
function stashDetection(sessionKey, detection):
    pendingDetections.set(sessionKey, detection)

// Hook B 消费检测结果 → 取出并删除（一次性）
function consumeDetection(sessionKey):
    detection = pendingDetections.get(sessionKey)
    pendingDetections.delete(sessionKey)
    return detection

// 调用流程：
// before_model_resolve → stash(sessionKey, {level, reason, desensitized})
//                  ↓
// before_prompt_build → consume(sessionKey) → 拿到检测结果，注入脱敏标记
```

这避免了全局变量或在 Hook 注册时传递参数，保持了各 Hook 的独立性。

#### 4.1.2 双轨记忆

系统维护两套平行的长期记忆：


| 记忆轨道          | 路径                                | 内容                         | 可见范围    |
| ------------- | --------------------------------- | -------------------------- | ------- |
| **Full**（完整）  | `MEMORY-FULL.md` + `memory-full/` | 包含所有信息，不做脱敏                | 仅本地模型可见 |
| **Clean**（脱敏） | `MEMORY.md` + `memory/`           | 过滤 Guard Agent 段落 + PII 脱敏 | 云端模型可见  |


双轨记忆需要双向同步：

```
// Full → Clean 方向：脱敏同步
function syncMemoryToClean(privacyConfig):
    // Step 0: 先把 Clean 的新增内容合并到 Full（确保 Full 是超集）
    mergeCleanIntoFull()

    fullContent = readFile("MEMORY-FULL.md")
    if fullContent is empty: return

    // Step 1: 过滤 Guard Agent 段落
    cleaned = filterGuardContent(fullContent)
    // 移除 [guard agent]、guard:、private context: 等标记下的段落

    // Step 2: PII 脱敏（优先端侧 LLM，降级正则）
    if privacyConfig and localModelAvailable:
        redacted = desensitizeWithLocalModel(cleaned, privacyConfig)
    else:
        redacted = redactSensitiveInfo(cleaned)
        // 正则替换 SSH keys, API keys, IPs, emails, 身份证, 手机号 等

    // Step 3: 写入 Clean
    writeFile("MEMORY.md", redacted)


// Clean → Full 方向：合并云端模型写入的新增内容
function mergeCleanIntoFull():
    cleanContent = readFile("MEMORY.md")
    fullContent  = readFile("MEMORY-FULL.md")
    if cleanContent is empty: return

    // 已有行集合（按 trim 后内容去重）
    fullLines = Set(fullContent.split("\n").map(trim).filter(nonEmpty))

    // 找出 Clean 中有、Full 中没有的新增行
    newLines = []
    for line in cleanContent.split("\n"):
        trimmed = line.trim()
        if trimmed and trimmed not in fullLines and not trimmed.includes("[REDACTED:"):
            newLines.push(line)

    if newLines is not empty:
        appendToFile("MEMORY-FULL.md", "\n\n## Cloud Session Additions\n" + join(newLines))
```

> **为什么需要 Clean → Full 的反向同步？** 云端模型在处理 S1 任务时可能写入有价值的公开信息（如从网络搜索获得的技术方案、公开 API 文档摘要）。这些内容存入了 MEMORY.md。如果不合并回 FULL，端侧模型会丢失这些上下文。FULL 必须始终是超集。

同步时机：

- 每次会话结束（`session_end` Hook）
- 会话压缩后（`after_compaction` Hook）
- 会话重置前（`before_reset` Hook）

#### 4.1.3 双轨会话历史

与双轨记忆类似，会话历史也分为两条轨道：


| 轨道        | 内容                     | 用途           |
| --------- | ---------------------- | ------------ |
| **full**  | 所有消息（含 Guard Agent 交互） | 本地审计、端侧模型上下文 |
| **clean** | 排除 Guard Agent 的交互     | 云端模型上下文      |


当云端模型读取会话历史时，自动使用 clean 轨道；当本地模型读取或审计需要时，使用 full 轨道。

此外，状态管理层还对云端模型的文件访问做了路径保护：对 `MEMORY-FULL.md`、`memory-full/`、`sessions/full/` 等路径的访问请求会被 Hook 拦截并重定向到对应的 clean 路径，确保云端模型无法绕过双轨机制直接读取完整数据。

### 4.2 性价比路由的状态管理

性价比路由的状态管理相对简单，主要是 **Token 统计** 和 **分类缓存**。

#### 4.2.1 Token 统计

按 tier 分别统计每次调用的 token 使用情况：


| 统计维度   | 字段                                                          |
| ------ | ----------------------------------------------------------- |
| 按 Tier | SIMPLE / MEDIUM / COMPLEX / REASONING 各自的请求次数、输入/输出 token 数 |
| 按时间    | 小时级聚合，用于 Dashboard 时间线展示                                    |
| 按会话    | 每个会话使用了哪些 tier、总 token 数                                    |
| 成本估算   | 根据各 tier 模型的单价估算实际费用和"如果全用最贵模型"的假设费用，计算节省金额                 |


#### 4.2.2 分类缓存

Token-Saver 的 LLM Judge 调用结果通过 Prompt Hash 缓存：


| 参数        | 默认值                    | 说明           |
| --------- | ---------------------- | ------------ |
| Cache Key | SHA-256(prompt) 前 16 位 | 内容相同的消息共享缓存  |
| TTL       | 5 分钟                   | 超时后重新分类（可配置） |
| 清理周期      | 60 秒                   | 定期扫描过期条目     |
| 最大存活      | 10 分钟                  | 硬上限，超时必删     |


### 4.3 共享状态：配置热更新

两个路由器共享一个配置热更新机制：

- 配置文件 `guardclaw.json` 支持运行时修改
- Dashboard 提供 `GET/POST /api/config` 接口读写配置
- 修改立即生效，无需重启
- 配置包括：检测规则（关键词、正则）、tier 到模型的映射、路由器启用/禁用、权重调整

## 五、可观测层

除了四层核心结构，系统还提供了一个可观测层——**Dashboard**，用于验证路由系统的行为是否符合预期。

Dashboard（Web UI）提供以下能力：


| 功能            | 说明                         |
| ------------- | -------------------------- |
| **统计概览**      | 总费用、各 tier 占比、累计节省金额       |
| **时间线**       | 小时粒度的请求分布和成本趋势             |
| **会话明细**      | 每个会话使用了哪些 tier、是否触发隐私路由    |
| **检测日志**      | 所有检测事件的时间线（等级、原因、命中的规则）    |
| **配置编辑**      | 实时修改路由规则、tier 映射，无需重启      |
| **Prompt 编辑** | 修改检测 prompt 和 Judge prompt |
| **干运行测试**     | 输入一段文本，预览其路由结果（不实际执行）      |


> **为什么需要 Dashboard？** Dashboard 不是"锦上添花"。路由系统是一个**自动化决策系统**，用户需要回答：路由决策是否正确？成本确实降低了吗？哪些消息被标记为敏感？在哪些 case 上分级不符合预期？没有 Dashboard，这些问题只能通过翻日志回答——对普通用户来说门槛太高。Dashboard 是路由系统可信度的基础设施。

## 六、两个路由器的四层总览

下表将两个内置路由器在四层结构上的实现进行对比总结：


| 层         | 隐私安全路由                                                             | 性价比路由                                                      |
| --------- | ------------------------------------------------------------------ | ---------------------------------------------------------- |
| **检测层**   | 双引擎（规则 + 端侧 LLM）→ S1/S2/S3 三级安全等级                                  | LLM-as-Judge（小模型裁判）→ SIMPLE/MEDIUM/COMPLEX/REASONING 四级复杂度 |
| **路由层**   | S1→passthrough, S2→proxy/local, S3→Guard Agent（weight=90, Phase 1） | 每个 tier→对应的 provider/model（weight=30, Phase 2）             |
| **执行层**   | S1 直通 / S2 本地脱敏代理 / S3 Guard Agent 物理隔离                            | 模型切换（通过 provider 镜像转发）                                     |
| **状态管理层** | 会话隐私标记（只升不降）+ 双轨记忆 + 双轨会话历史 + 路径保护                                 | Prompt Hash 缓存 + 按 tier 的 token 统计 + 配置热更新                 |


两个路由器通过路由管线的**两阶段执行**和**加权决策合并**自然协作：

- 隐私安全路由在 Phase 1 运行，优先判断安全性
- 检测到隐私问题（S2/S3）→ 短路，隐私路由胜出
- 未检测到隐私问题（S1）→ 隐私路由返回 passthrough，让性价比路由在 Phase 2 做成本优化
- 性价比路由的 redirect 在 S1 场景下自然生效

这个设计实现了"**安全是前提，成本优化是在安全通过后的第二级关注**"的协同目标。
