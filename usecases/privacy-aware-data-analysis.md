# 隐私数据分析：财报与病历

企业内部数据分析的核心矛盾：大模型的分析推理能力很强，但你不能把原始财务数据或患者病历直接丢给云端。手动脱敏？你自己都分析不完，何况脱敏。

这个 use case 用 GuardClaw 让本地小模型负责 SQL 取数 + 自动脱敏，云端大模型只看到脱敏后的数据集和统计摘要，产出深度分析报告。

## Pain Point

- 财务数据包含公司核心商业秘密（收入细节、客户名单、利润率）
- 医疗数据受 HIPAA/个保法等严格监管，患者 PII 泄露是法律事件
- 大模型的分析和报告能力远超小模型，但合规不允许数据出本地
- 手动脱敏费时且容易遗漏（一个没脱掉的名字就是合规事故）

---

## 场景 A：财报分析

### 工作原理

```
"帮我分析 Q4 各产品线的营收趋势"
         │
         ▼
[S3 本地 Guard Agent]
│  ① 生成并执行 SQL 查询（连接内部数据库）
│  ② 拿到原始数据：
│     产品A  ¥12,345,678  客户X  合同号xxxxx
│  ③ 自动脱敏：
│     - 绝对数字 → 相对指数（基数=100）或百分比
│     - 客户名 → Customer-001
│     - 合同号 → [CONTRACT-REDACTED]
│     - 保留趋势和比例关系
│  ④ 输出脱敏数据表 + 基础统计量
         │
         ▼ 脱敏后的数据表
[S1 云端大模型]
│  ⑤ 趋势分析（哪条产品线在增长/下降）
│  ⑥ 异常检测（Q4 某产品线为何骤降？）
│  ⑦ 行业对比视角（增速 vs 行业平均）
│  ⑧ 战略建议（资源应该向哪倾斜？）
│  ⑨ 生成管理层可读的分析报告
         │
         ▼
[S3 本地 Guard Agent]
│  ⑩ 将报告中的占位符还原为真实数据
│     "产品线 Alpha（指数 142）" → "产品A（¥12,345,678）"
│  ⑪ 保存完整报告到本地
```

### 模型分工

| 阶段 | 模型 | 敏感级别 | 说明 |
|------|------|----------|------|
| SQL 生成 + 执行 | 本地小模型 | S3 | 接触原始数据库 |
| 数据脱敏 + 指数化 | 本地小模型 | S3 | 绝对值→相对值，保留趋势 |
| 深度分析 + 洞察 | 云端大模型 | S1 | 只看指数和百分比 |
| 报告生成 | 云端大模型 | S1 | 结构化的分析报告 |
| 占位符还原 | 本地小模型 | S3 | 最终报告在本地还原真实数字 |

## 场景 B：病历分析

### 工作原理

```
"帮我分析这批糖尿病患者的治疗方案有效性"
         │
         ▼
[S3 本地 Guard Agent]
│  ① SQL 查询 HIS/EMR 系统
│  ② 拿到原始病历：
│     张三 身份证310xxxxx 2型糖尿病 HbA1c 8.2%
│     李四 身份证110xxxxx 2型糖尿病 HbA1c 7.5%
│  ③ 自动脱敏：
│     - 姓名 → Patient-001, Patient-002
│     - 身份证/医保号 → [ID-REDACTED]
│     - 就诊医院/医生 → [HOSPITAL-A], [DOCTOR-1]
│     - 保留：年龄段、性别、诊断、指标数值、用药方案
│  ④ 输出脱敏患者队列表
         │
         ▼ 脱敏后的临床数据
[S1 云端大模型]
│  ⑤ 治疗方案对比分析（哪种方案 HbA1c 下降更多）
│  ⑥ 亚组分析（按年龄段、合并症分层）
│  ⑦ 引用最新临床指南评估方案合理性
│  ⑧ 生成临床研究风格的分析报告
│  ⑨ 建议可能的方案调整方向
```

### 模型分工

| 阶段 | 模型 | 敏感级别 | 说明 |
|------|------|----------|------|
| EMR 查询 | 本地小模型 | S3 | 接触原始病历 |
| PII 去标识化 | 本地小模型 | S3 | 保留临床指标，去除身份信息 |
| 临床分析 | 云端大模型 | S1 | 只看脱敏后的数据 + 临床指标 |
| 指南引用 + 文献支持 | 云端大模型 | S1 | 结合最新循证医学知识 |

## Prompt 示例

### 财报分析

```text
帮我分析公司 2025 年 Q1-Q4 各产品线的营收变化趋势。

数据在内部 PostgreSQL，连接信息在 .env 里。
我需要：
1. 各产品线季度环比和同比增速
2. 毛利率变化
3. 表现最好和最差的产品线分析
4. 2026 年的资源分配建议

注意：所有数据脱敏后再分析，报告里不要出现具体金额，用指数或百分比表示。
```

### 病历分析

```text
分析我们内分泌科过去一年的 2 型糖尿病患者数据。

数据源：HIS 系统 MySQL 数据库
分析要求：
1. 不同治疗方案（二甲双胍单药 vs 联合用药）的 HbA1c 控制率对比
2. 按年龄段（<40, 40-60, >60）分层分析
3. 平均达标时间
4. 对照 ADA 2025 指南评估方案合理性
5. 建议可优化的治疗路径

所有患者信息必须脱敏处理。
```

## 期待结果与效果预估

> **一句话**：原始数据零泄露，分析洞察质量损失仅约 5-15% — 趋势、比例、排名等相对分析不受影响，仅绝对量级信息需本地还原。

### 隐私保护效果

**财报场景：**

| 数据类型 | 脱敏方式 | 信息保留度 |
|----------|---------|-----------|
| 绝对金额 | 指数化（Q1=100 基准） | 趋势和比例 100% 保留，绝对量级丢失 |
| 客户名称 | Customer-001/002 | 客户间的对比关系保留 |
| 合同号 | [CONTRACT-REDACTED] | 合同数量和分布保留 |
| 利润率/增长率 | 百分比直接保留 | 100% 无损 |

**病历场景：**

| 数据类型 | 脱敏方式 | 信息保留度 |
|----------|---------|-----------|
| 患者姓名 | Patient-001/002 | 队列对比关系保留 |
| 身份证/医保号 | [ID-REDACTED] | 完全移除 |
| 临床指标（HbA1c、血压） | 原值保留 | 100% 无损 |
| 年龄段/性别 | 原值保留 | 100% 无损 |
| 医院/医生 | [HOSPITAL-A]、[DOCTOR-1] | 机构间对比保留 |

### 质量影响预估

| 维度 | 影响程度 | 说明 |
|------|---------|------|
| 趋势分析（环比/同比） | **无损** | 指数化完整保留趋势 |
| 异常检测 | **无损** | 相对偏差仍可识别 |
| 行业对比 | **略降（~10-15%）** | 绝对量级缺失，无法与行业基准直接比较 |
| 亚组分析 | **无损** | 分层数据完整 |
| 战略建议 | **略降（~5-10%）** | 缺乏绝对规模信息，建议的量级感可能偏差 |

### 成本对比

| 方案 | 本地处理（SQL+脱敏+还原） | 云端分析 | 总计 |
|------|------------------------|---------|------|
| 纯云端 | $0 | ~$2-10 | ~$2-10 |
| GuardClaw 混合 | ~$0.05-0.20（LLM 脱敏） | ~$2-10（不变） | ~$2-10 + 极少检测开销 |

核心收益在**合规性**（HIPAA/个保法）和**商业秘密保护**，不在省钱。

### 延迟影响

- SQL 查询 + 脱敏处理：~5-15s（取决于数据量）
- 云端分析：~30s-2min（不变）
- 本地还原：~1-3s
- **总增加延迟**：~10-20s

### 风险与局限

- 指数化后无法做绝对金额相关的分析（如 "收入是否达到 10 亿门槛"）
- SQL 生成可能取出不必要的敏感字段（需配合 `onToolCallProposed` 检查）
- 病历中的自由文本（主诉、病程记录）可能包含间接 PII
- 小样本数据（如仅 3 个客户）脱敏后仍可能被推断还原

## 关键洞察

- **指数化而非简单替换**：财报场景中，用 `[REDACTED]` 替换金额会让分析失去意义。正确做法是转为相对指数（Q1=100 基准）或百分比，保留趋势信息
- **最后一步还原**：云端产出的报告用占位符，本地 Agent 在最终步骤替换回真实数字，完整报告只存在本地
- **病历的 Safe Harbor 标准**：HIPAA Safe Harbor 要求去除 18 类标识符。本地模型需要对照这个清单做脱敏
- **SQL 注入防护**：本地小模型生成 SQL 时，GuardClaw 的 `onToolCallProposed` checkpoint 可以拦截危险查询
- **数据最小化**：SQL 查询就做好字段筛选，不要 `SELECT *` 拿出不需要的敏感字段
